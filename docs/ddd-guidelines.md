# DDD の設計判断ガイド

この文書は、DDD の構成を先に固定するためのものではありません。題材を決めた後、業務上の概念とルールをコードへ反映するときの判断基準を共有するための下書きです。

## モデルを作る順序

1. 対象とする業務、利用者、解決したい問題を具体的にする。
2. 業務で使われる言葉と意味を集め、ユビキタス言語として揃える。
3. 同じ言葉やルールが一貫した意味を持つ範囲を見つけ、境界づけられたコンテキストを定める。
4. コンテキスト内のユースケースと、常に守るべき業務ルールを列挙する。
5. 一貫性を同時に守る必要がある範囲を集約とし、その入口となる集約ルートを決める。
6. 外部システム、永続化、UI との接続は、ドメインモデルの外側に置く。

この順序は、最初から正確なモデルを完成させることを求めません。実装を通して理解が変わったら、言葉、境界、モデルを見直します。

## 依存方向

基本の依存方向は次のとおりです。

```text
presentation / infrastructure -> application -> domain
```

- `domain` は業務ルールを表し、他のレイヤーへ依存しない。
- `application` はユースケースを進行し、ドメインオブジェクトを組み合わせる。業務ルールそのものは持ち込まない。
- `infrastructure` はデータベースや外部APIなどの技術的な詳細を実装する。
- `presentation` はHTTPやCLIなどの入力をアプリケーション層へ渡し、結果を外部向けの表現へ変換する。

依存性注入の仕組みやフレームワークは、この方向を保つために必要になった時点で選びます。

## モデリング要素の採用基準

### Entity

属性が変化しても同一性を追跡する必要がある概念に使います。単にデータをまとめる目的では使いません。

### Value Object

値そのものによって等価性が決まり、その値に関する検証や振る舞いをまとめたい概念に使います。生成後に値を変更しない設計を基本とします。

### Aggregate

業務上の不変条件を一度の操作で守る必要がある範囲に使います。外部からの変更は集約ルートを通し、必要以上に大きな集約にはしません。

### Domain Service

重要な業務ルールでありながら、特定の Entity や Value Object の責務として自然に置けない振る舞いに使います。ユースケースの進行や外部I/Oの都合を置く場所にはしません。

### Repository

集約の取得と保存を、永続化方式から切り離す必要がある場合に使います。ドメインまたはアプリケーション側が必要な操作をインターフェースとして定義し、インフラストラクチャ側が実装します。テーブル単位の汎用CRUDにはしません。

## 題材決定後の構成例

構成はモデルとユースケースが見えてから作ります。必要になった場合は、次のような分割を候補にします。

```text
src/
  domain/
  application/
  infrastructure/
  presentation/
```

これは固定のテンプレートではありません。小さなコンテキストでは機能単位でまとめるなど、コード上の責務と依存方向が伝わる最小の構成を選びます。

## 現段階の方針

- 具体的な題材とユビキタス言語が決まるまで、ドメインモデルは実装しない。
- コードを置く目的がない空のレイヤーディレクトリは作らない。
- `src/greeting.ts` はツールチェーン確認用であり、ドメインモデルとして発展させない。
- 設計判断が増えたらテーマごとに `docs/*.md` へ分割し、README から参照できるようにする。
