# 技術スタックを選ぶ

TypeScriptとDDDの学習に用いる技術を、役割と採用理由とともに定める。技術を追加するときはこのADRへ選定内容を追記し、各機能の実装範囲・API契約・受入条件は対応するIssueで定める。手元で動かす最短経路は[README](../../README.md)、接続先やスキーマ反映・実DB検証の詳細は[ローカル開発](../local-dev.md)を参照する。

## バックエンド

| 役割         | 採用する技術                       |
| ------------ | ---------------------------------- |
| 実行環境     | Node.js                            |
| HTTP API     | Hono                               |
| 開発サーバー | Viteと`@hono/vite-dev-server`      |
| 入力検証     | Valibot                            |
| DBアクセス   | Drizzleとnode-postgres             |
| データベース | Docker Composeで起動するPostgreSQL |

HonoによるAPI開発を学習対象とし、Viteの開発サーバーでローカル実行する。PostgreSQLは、トランザクション内でTypeScriptのドメイン判定を使え、独立した接続間で排他を検証できるため選ぶ。DrizzleはSQLとトランザクションを明示して扱うために採用する。DBだけをDockerで起動し、アプリケーションはホスト上のNode.jsで動かす。本番環境へのデプロイや特定のクラウドサービスへの適合は、この学習環境の成立条件にしない。

モジュール解決はTypeScriptのBundlerとし、相対importに拡張子は書かない。配布用のJavaScriptは出さない。型検査はoxlintのtype-aware / type-checkに寄せ、`tsc`のemitはcheckに含めない。Vite+への移行は今は行わない。

HonoはHTTP入出力の変換、Valibotは入力の構造と型の検証、DrizzleはSQLと永続化マッピングに使用する。バックエンドの層構成、各層の責務・依存方向、Composition Rootの役割は[ADR-0012](./0012-backend-layered-directory-structure.md)で定める。

スキーマ管理は、SQLとスナップショットによるマイグレーション履歴の管理から、TypeScriptのスキーマを正とするDrizzle Kitのpush方式へ変更する。モデルが変わりやすいローカル開発段階では、生成物と適用履歴の管理を省いて環境を簡素に保つためである。開発DBと専用テストDBで同じスキーマを反映し、反映対象は`public`に限定する。スキーマ反映と機材シードはアプリケーション起動から分離する。

この方式は、共有環境や本番環境へ順序付きの変更を配布する必要がない間に限る。開発DBでは適用するSQLを表示し、追加の変更は確認なしで入れる。データ損失を伴う変更は強制適用しない。テストでもデータ損失の警告があれば反映を中止する。配布可能な変更履歴やデータ移行の再現性が必要になった時点で、マイグレーション履歴を管理する方式を再検討する。

Composeはローカルの開発用PostgreSQLを起動し、接続をループバックに限定してデータをボリュームへ保持する。テスト用PostgreSQLは、テスト実行に合わせて寿命を管理できるTestcontainersへ移す方針だが、導入は別の作業とする。それまでは専用の`test-db`をComposeに残し、開発データから分離した実DB検証を継続する。

## フロントエンドの採用方針（未導入）

React・Vite・TanStack RouterによるSPAを採用し、APIとの型共有にはHono RPCを使う。ブラウザとサーバーをHTTP APIで分け、ドメイン集約やDB処理の実装はブラウザへ持ち込まない。

APIとフロントを別パッケージとして扱う必要が生じた時点で、pnpm workspacesによるモノレポ構成を導入する。それまでは単一パッケージとし、共有する目的のないパッケージは作らない。
