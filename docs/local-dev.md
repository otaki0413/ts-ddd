# ローカル開発

最短経路は[README](../README.md)を参照する。ここでは接続先、スキーマ反映、実DB検証の注意を書く。

## 環境変数と接続先

`.env`の2種類のパスワードをそれぞれローカル専用の値へ変更し、対応するURLにも同じ値を設定する。URLの予約文字を含むパスワードはURL内でパーセントエンコードする。`.env`はGit管理外である。既存の`.env`やDBのパスワードを上書きしない。

DB接続はサーバー専用の`DATABASE_URL`、テストは`TEST_DATABASE_URL`を使う。`VITE_*`には置かない。開発DBは`127.0.0.1:55432/ts_ddd`、テストDBは`127.0.0.1:55433/ts_ddd_test`である。既存の5432番ポートのDBは使わない。

DBだけをDocker上のPostgreSQL 18.4で動かし、APIはホストのNode.js上で実行する。初回はイメージ取得が必要である。`db:up`はDBが接続可能になるまで待つ。シードは利用可能な`EQ-001`と`EQ-002`を追加し、繰り返しても既存の機材状態を上書きしない。

APIはCtrl-C、DBは`pnpm db:stop`で停止する。再開時は`pnpm db:up`と`pnpm dev`を実行する。

## スキーマ反映

ローカル開発では[src/infrastructure/postgres/schema.ts](../src/infrastructure/postgres/schema.ts)を正として、`.env`を読む`db:push`で`public`スキーマへ反映する。マイグレーションSQLやスナップショットの履歴は管理しない。適用するSQLは表示される。追加の変更は確認なしで入り、変更がなければ何も変わらない。データ損失の警告が出た場合は中止し、既存データを保つ変更方法を検討する。`--force`やボリューム削除で回避しない。以前のマイグレーションで作成済みの`drizzle`スキーマはpushの対象外で、履歴を削除する必要はない。

## 検証

実DBテストは専用の`ts_ddd_test`へDrizzle Kitのpush APIで同じTypeScriptスキーマを反映し、そのDBの機材・予約をテストごとに初期化する。DBが起動していない場合はスキップせず失敗する。`pnpm test:db -t 'テスト名'`で絞り込める。スキーマ反映がデータ損失を伴うと判定された場合は適用せず失敗する。pushの対象は`public`だけで、時刻制御用の`test_clock`スキーマは対象外である。接続先のホスト・ポート・DB名・ユーザーを検査し、開発DBへ接続する設定では実行しない。テストDBは専用コンテナのtmpfsに置き、停止するとデータが失われる。同じテストDBを使うテストコマンドは同時に実行しない。

Composeの`test-db`は暫定構成である。今後、テスト用PostgreSQLをTestcontainersで起動し、Composeは開発DBだけを担当する方針だが、Testcontainersはまだ導入していない。

主な検証境界はHonoのHTTP要求から既存ユースケース、実Drizzleアダプタ、PostgreSQLまでである。Vite+の実設定も一時ポートで起動し、作成・読み戻し・JSONエラーを確認する。同時予約では両方の事前確認を待ち合わせ、独立した接続がDB上でロック待ちすることを観測してから解放し、成立件数を確認する。時刻境界ではテスト専用スキーマのDB時計を制御する。通常のテストと開発APIでは実際の`clock_timestamp()`を使い、アプリの時計だけの固定で代用しない。遅延制約の障害注入もテストDB内だけで行う。
